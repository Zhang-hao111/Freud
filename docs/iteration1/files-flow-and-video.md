# 迭代一文件、流程、验收与视频演示指南

## 1. 文档范围

本文只说明“迭代一：Agent 驱动的 Hadoop 数据清洗与五维质量评估”，不讨论迭代二的分类、聚类、降维，也不讨论迭代三的知识图谱、推荐和图算法。

本文用于四件事：

1. 说明迭代一相关文件分别负责什么；
2. 说明从一次自然语言请求到 Hadoop 产物和前端展示的完整流程；
3. 按迭代一原文给出测试、验收证据和当前未验证范围；
4. 给出约 10 分钟演示视频的画面、讲解词、提示词和时间规划。

必须区分以下三种结果：

- **真实 Hadoop 分布式运行**：任务在 HDFS/YARN 或等价集群环境中运行；
- **真实 Hadoop 本地模式运行**：由 Hadoop 3.4.1 的 `FsShell`、`RunJar`、Streaming 和 `LocalJobRunner` 实际执行，但文件系统为 `file:///`，不是多节点 HDFS/YARN；
- **Python 单元测试或规则直跑**：只验证 worker 和业务逻辑，不得当作 Hadoop 端到端结果。

2026-09-29 的本轮测试属于第二种：**真实 Hadoop Streaming 本地模式，不是模拟，但也不是分布式集群测试**。根据本轮测试要求，未运行 116 万行原始数据的全量作业；所有具体分数均来自 17 条记录的微型验收数据，不能作为 MovieLens 1M 全量评分引用。

## 2. 需求到实现的对应关系

| 迭代一要求 | 实现入口 | 主要证据 |
| --- | --- | --- |

| 区分修复、去重、隔离 | `clean_map()`、`split_clean()` | `actions` 计数、处置样例和只包含真正隔离项的 `quarantine.jsonl` |
| 提供数据版本、规则版本和任务标识 | `pipeline.py` | `task_id`、`source_version`、`data_version`、`rule_version`、`score_version` |
| 生成并登记 `T1/T2` | `cutoff()` | 清洗后有效评分的 80%/90% 时间分位日末，且必须满足 `T1<T2` |

| 未完成或失败时不得伪造结果 | `HadoopGovernanceTool.execute()`、Web 状态判断 | Hadoop 错误原样转成失败状态；未完成追问返回 HTTP 409 |

### 3.5 运行后产物

默认本地产物位于 `governance-runs/{task_id}/`；Hadoop 路径记录在 `report.json` 的 `hdfs_run` 字段中。

| 产物 | 作用 |
| --- | --- |
| `audit-before.jsonl` | 清洗前逐条审计结果，包括原始值、规范值和异常标签。 |
| `score-before.jsonl` | Hadoop 聚合后的清洗前总数、表计数、异常计数、维度分子/分母、日期分布和五维得分。 |
| `clean-initial.jsonl` | 第一次清洗判定，用于先生成有效用户和电影引用集合。 |
| `references/users.dat`、`references/movies.dat` | 第一次清洗后保留的实体引用；第二次清洗据此重新检查评分外键。 |
| `references/ratings.dat` | 引用准备阶段的空占位文件；评分引用不用于实体集合。 |
| `clean-final.jsonl` | 最终逐条处置结果；每条记录明确标记 `keep`、`repair`、`deduplicate` 或 `quarantine`。 |
| `cleaned/users.dat`、`movies.dat`、`ratings.dat` | 清洗后有效数据；`keep` 和 `repair` 项进入这些文件。 |
| `cleaned/quarantine.jsonl` | 只保存 `quarantine` 项。去重记录不会混入此文件，避免把“去重”误报为“隔离”。 |
| `audit-after.jsonl`、`score-after.jsonl` | 对清洗产物使用同一套规则复检和复评的结果。 |
| `report.json` | 机器可读的完整报告，是前端和追问的事实来源。 |
| `report.md` | 供下载、提交和人工审阅的 Markdown 报告。 |
| `failure.json` | 失败任务的阶段和错误；只有失败时生成，不与成功报告混用。 |

使用 Hadoop 本地文件系统时，可能看到 `.crc` 校验边车文件；它们由 Hadoop 文件系统实现生成，不是业务报告，也不应在演示中解释为额外数据记录。

### 3.6 不进入迭代一治理主流程的文件

- `config.json`、`agent/llm.py` 和 PackyAPI/DeepSeek 配置服务于通用 `freud` Coding Agent，不被 `freud-governance` 的 Hadoop 治理 Web 流程读取。
- 治理追问优先由大模型生成解释：复用实验一的 LLM 接入层（`agent/llm.py`，OpenAI 兼容接口含重试），模型配置读取 `config.json` 或环境变量；`report_digest()` 抽取的报告摘要是唯一事实源，提示词要求报告外信息必须回答"报告中未包含"。API 调用失败或未配置 Key 时自动回退 `explain()` 模板回答，`--no-llm` 可强制模板模式。回答接口附带 `mode` 字段（`llm` / `template`），前端在回答末尾标注来源。
- 演示时不要打开 `config.json`，不要在终端历史、浏览器地址栏或视频字幕中展示 API Key；报告摘要仅包含任务报告内容，不包含密钥或代码。
- `docs/design.md`、`docs/debug-log-lab2.md` 主要描述通用 Coding Agent，不是迭代一 Hadoop 验收证据。

## 4. 完整运行流程

### 4.1 从页面到 Agent 工具

1. 用户在页面输入自然语言请求，点击“开始清洗与评估”。
2. 页面向 `POST /api/jobs` 发送 `prompt`，可选携带原始数据、清洗规则和评分规则版本。
3. `GovernanceAgent.start()` 验证：
   - 提示词必须是非空文本；
   - 目标必须与 MovieLens 清洗、治理或五维评估有关；
   - 当前只接受已登记的默认规则版本；
   - 指定的原始版本必须是 16 位十六进制版本号。
4. Agent 生成 32 位任务 ID，返回 `running`，并在线程中启动 `HadoopGovernanceTool`。
5. 页面按任务 ID 轮询 `GET /api/jobs/{id}`，显示当前阶段；未完成时不显示结果卡片。

### 4.2 Hadoop 内部数据流

```text
原始 users/movies/ratings
        │
        ├─ 上传原始文件与 worker.py
        │
        ├─ audit-before
        │    audit-map → shuffle/sort → audit-reduce
        │
        ├─ score-before
        │    score-map → score-combine → score-reduce
        │
        ├─ clean-initial
        │    clean-map → 生成有效 users/movies 引用
        │
        ├─ clean-final
        │    clean-map → keep / repair / deduplicate / quarantine
        │
        ├─ 上传 cleaned 三表
        │
        ├─ audit-after
        │    使用与清洗前完全相同的审计规则
        │
        ├─ score-after
        │    使用与清洗前完全相同的评分规则
        │
        └─ 对账、版本哈希、T1/T2、report.json、report.md
```

页面显示的阶段将内部作业合并为更容易理解的五段：上传、清洗前检查、清洗前评分、清洗及关联核对、清洗后复评。报告只有在所有内部作业成功、记录对账成立且 `T1<T2` 时才生成。

### 4.3 解析、业务键和确定性

- 三个文件均按 ISO-8859-1 解码，按 `::` 分隔，不读取表头。
- `users` 的业务键为 `UserID`；`movies` 的业务键为 `MovieID`；`ratings` 的业务键为 `(UserID, MovieID, Timestamp)`。
- 同一用户在不同时间对同一电影评分会保留，不会因 `(UserID, MovieID)` 相同而误删。
- 同键不同规范值标记为冲突并隔离；同键同值只保留一条，其余去重。
- Hadoop shuffle 不保证同一键下 value 顺序，因此 reducer 按关键异常数量、异常集合、规范值和原始值排序，保证同一输入和规则版本得到稳定的保留项与计数。

### 4.4 处置规则

处置优先级为：

1. 字段数量、缺失、值域、时间、引用或冲突等关键问题：`quarantine`；
2. 完全重复：`deduplicate`；
3. 只有可确定的格式规范化问题：`repair`；
4. 无异常：`keep`。

程序不会猜测缺失值，不会为了提高分数任意修改冲突内容，也不会把隔离说成修复。最终必须满足：

```text
清洗前总数 = 清洗后总数 + 去重数 + 隔离数
```

`repair` 不减少记录数，因此包含在清洗后总数中。异常标签允许重叠，所以异常标签数量之和不一定等于处置记录数量。

### 4.5 五维评分口径

每个维度使用：

```text
得分 = 100 × 通过记录数 / 该维度适用记录数
```

空分母返回 `null`，不返回假 100 分。

| 维度 | 通过条件 | 必须说明的局限 |
| --- | --- | --- |
| Accurate | 必填、类型、值域和历史时间范围均通过 | 只能验证规则内表面正确性，不能证明自报属性或电影信息真实 |
| Complete | 字段数正确且必填字段非空 | 不能推断业务上未提供但文件规范未要求的属性 |
| Unique | 业务键不重复、不冲突且可解析 | 评分键包含时间，不同时间的同用户同电影评分不是重复 |
| Up-to-date | 仅评分表；时间位于发布日前一年，即 2002-02-28 至 2003-02-28 | 参照的是历史数据集发布日，不代表 2026 年的“新鲜度” |
| Consistent | 字段格式、类别、时间、外键和同键内容无矛盾 | 不能自动判定同名电影、异常评分行为或用户填写内容是否可信 |

### 4.6 版本与时间边界

- `source_version`：三个原始文件 SHA-256 映射再次哈希后的 16 位标识；
- `data_version`：三个清洗文件 SHA-256 映射再次哈希后的 16 位标识；
- `rule_version`：当前为 `ml1m-governance-v1`；
- `score_version`：当前为 `ml1m-five-dim-v1`；
- `T1`：清洗后有效评分按日期累计达到 80% 时的当天 23:59:59 UTC；
- `T2`：累计达到 90% 时的当天 23:59:59 UTC。

如果没有有效评分、日期分布不足或 `T1>=T2`，任务失败，不生成伪造边界。

### 4.7 完成后的页面与追问

完成后页面显示：

- 五维清洗前、清洗后和变化值；
- 原始/清洗后总数以及修复、去重、隔离数量；
- 任务、原始数据、清洗数据、清洗规则和评分规则版本；
- `T1/T2`；
- 评分口径、局限、代表性记录及其处置；
- 报告下载和清洗后评分样例；
- 基于当前报告的追问回答。

任务未完成时追问返回 HTTP 409；任务不存在返回 404；非法 JSON、无关提示词或未登记规则返回 400。

## 5. 2026-09-29 实际测试记录

### 5.1 环境与范围

- Python 3.14.6；
- OpenJDK 21；
- Apache Hadoop 3.4.1 官方 Maven 构件；

### 5.2 真实 Hadoop Streaming 结果

```text

已完成
```

| keep | 14 |
| repair | 0 |
| deduplicate | 1 |
